# Step 5: C4

> Running example: a **personal trainer** app.

## What it is
The first diagrams, derived from the requirements. The "4" in C4 is the number of abstraction
levels the model offers, not the number of diagrams you must draw:

1. **Context:** the system among its users and external systems.
2. **Containers:** the deployable pieces inside it.
3. **Components:** what lives inside one container.
4. **Code:** classes and schemas.

The model's author treats Context and Containers as the usual stopping point. Draw a Component
diagram (level 3) only for a container complex enough to warrant it, and almost always skip Code (level 4),
since the IDE generates it. So a design package with only Context and Containers
is not an unfinished C4, it is the standard altitude for this work.

## What goes inside
- **Context:** the system, its actors (from the roles in the requirements), and external
  systems it talks to.
- **Containers:** the runnable parts (app, API, database, the AI component) and how they
  connect.

Write it as Structurizr DSL so both diagrams come from one model and can't drift apart. The
container names you pick here are load-bearing: **OpenAPI tags will equal these container
names** at step 6.

## Two paths, and when to take the second one

**Code, the default.** Structurizr DSL, [`templates/c4-workspace.dsl`](../templates/c4-workspace.dsl).
Both views come from one model, layout is automatic, the DSL validates, and the consistency gate
reads container names straight out of it. Take this path unless something below applies.

**Canvas.** A native draw.io file, [`templates/c4.drawio`](../templates/c4.drawio). Boxes are real
editable shapes, so a stakeholder or an architect can drag them in the browser and hand the file
back, and you read and edit the XML. Worth it when the layout itself carries meaning, when the
person who must approve the diagram works in draw.io and will not read a DSL, or when someone
outside the project has to edit it without installing anything.

Do not import PlantUML into draw.io hoping for the middle ground: it lands as a picture, not as
shapes, and you get neither editing nor a model.

**What the canvas costs, stated plainly.** Nothing validates a `.drawio` file. There is no renderer
to fail, no model to check the two views against each other, and the consistency gate cannot read
container names out of it, so on this path the names are yours to keep aligned by hand. Choose it
for the reason above, not for the pretty boxes, and expect to check by eye what the other path
checks by tool.

## What the text looks like
A `.dsl` model, rendered to PNG or SVG. Names match the requirements exactly.

```
user = person "User" "Sets a goal, logs sessions"
trainer = softwareSystem "Personal Trainer" {
  api = container "Plan API" "Generates and serves TrainingPlans"
  adapter = container "Adaptation Engine" "Adapts a plan from Sessions and Metrics"
  db = container "Database" "PostgreSQL" "PostgreSQL 16" "Database"
}
wearable = softwareSystem "Wearable Provider" "Source of Metrics"
```

The identifier goes on the left of the `=`, and the name is the first quoted string. That order
matters: `container api "Plan API"` is not valid DSL and Structurizr will refuse it.

Render with [`tools/c4-render.sh`](../tools/c4-render.sh).

Record these container names in the [glossary](../templates/glossary.md) under Containers; OpenAPI tags and sequence participants reuse them verbatim.

## Which diagram
This step is the diagram. Context first (who and what around the system), then Containers (what
runs inside). Keep both diagrams readable: the standard C4 palette is fine, decoration for its own
sake is not the point.

## What does NOT go in
Containers you can't trace to a requirement, and colors that imply meaning you haven't defined.
If a box has no FR behind it, either it's missing from the requirements (open question) or it
doesn't belong.

## How to validate
On the canvas path, none of this applies: the file has no validator and no renderer. Check the
container names against `glossary.md` by hand, and know that step 9 will not catch a drift the DSL
path would have caught.


It renders from the DSL with no errors, and every actor and external system appears in the
requirements. The container list is the decomposition you will reuse as OpenAPI tags.

## Signs it's good
- Context and Containers at minimum, a Component diagram only for a container that needs it, no
  Code-level diagrams.
- Every actor and external system traces to the requirements.
- Container names are the ones you'll use as OpenAPI tags at step 6.
- It renders cleanly from a single DSL source.

Start from [`templates/c4-workspace.dsl`](../templates/c4-workspace.dsl), which validates as it
stands, and replace the placeholders with your own containers.

See this step's output in the example package: [`c4/workspace.dsl`](../example/c4/workspace.dsl) and the rendered [`c4/diagrams/`](../example/c4/diagrams).
